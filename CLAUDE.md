# polyclaude

The entry point to Claude Code — pick any directory, resume any session. Built with Python curses, single file, zero deps.

## Project structure

```
src/polyclaude/
  __init__.py          # package marker
  main.py              # all logic — config, parsing, TUI, entry point
  _version.py          # auto-generated by hatch-vcs (gitignored)
pyproject.toml         # hatchling + hatch-vcs build, entry point: polyclaude -> main:main
install.sh             # interactive installer (asks binary name, runs uv tool install)
```

Single-file architecture — everything lives in `main.py`. No runtime dependencies.

## Tabs

- **Start** (tab 0): one screen, two sections. *Running*: live sessions from `claude agents --json` (polled every 2 s by `LivePoller` on a daemon thread) with status (busy / waiting / idle), name, cwd, kind; Enter attaches to a background session. Interactive (`terminal`) sessions are foreground `claude` processes owned by another terminal: they can't be attached, and Enter names their tty instead. *New session in*: cwds from session history, current dir pinned, with a running count; Enter launches `claude`. The cursor follows the selected item by identity (`item_key`) across live-list refreshes.
- **Resume** (tab 1): existing picker. `/` to search session text, Enter to expand, Enter again to resume. Rows of running sessions carry a `● status (kind)` marker; Enter on a running background session attaches instead of resuming a copy.
- **Settings** (tab 2): list of toggles. Space/Enter toggles; saved immediately to `~/.config/polyclaude/config.json`.

`Tab` cycles 0 → 1 → 2 → 0. Tab indices are the `TAB_*` constants.

## Key design decisions

- **Pure stdlib**: only `curses`, `json`, `argparse`, `textwrap`, `dataclasses`. No pip deps.
- **Lazy loading, three tiers**: the screen must appear without reading whole session files (they reach 100+ MB).
  1. Startup: `scan_session_meta` reads only the head (sessionId, cwd, first user message) and the last 256 KB (last user message, last activity time, `custom-title`; falls back to the re-appended `last-prompt` line when tool output pushes the last user message out of the tail).
  2. Background: `start_stats_loader` runs a full `parse_session` per session on a daemon thread and fills counters/duration (`stats_loaded`). The TUI polls with `stdscr.timeout(150)` until it finishes, then blocks again.
  3. On demand: `raw_content` is read on the first `/` search (`ensure_raw`); the full conversation on expand (`load_messages`).
- **Cached cwd peek**: New tab needs the `cwd` of every session jsonl. It reads the first ~5 lines of a file once and caches `{path: cwd}` in `~/.cache/polyclaude/cwds.json` (XDG-aware via `XDG_CACHE_HOME`). A session's cwd never changes, so entries need no invalidation; only new files are opened. Files with no cwd yet are not cached.
- **Binary configurable**: `--binary` flag or `CLAUDE_BINARY` env var. Defaults to `claude`.
- **exec-based launch**: uses `os.execvp` after `os.chdir` — replaces the process entirely, so the resumed Claude session inherits the correct cwd.
- **Background launch (default)**: with `background` on, polyclaude runs `claude --bg [--resume <id>]` in the cwd, parses the id from its `claude attach <id>` hint, then execs `claude attach <id>`. The session lives in Claude's background host, not under this terminal, so it survives ssh drops; `attach` is only a viewer. `--fg` forces the old foreground exec for one run.
- **Persistent config** at `~/.config/polyclaude/config.json` (XDG-aware via `XDG_CONFIG_HOME`). Schema: `{"skip_permissions": bool, "background": bool}`. `skip_permissions` defaults to `false` (permissions enforced), `background` to `true`; toggles auto-save. Enable in config/Settings to skip permission prompts.
- **`--unsafe` CLI flag** forces `--dangerously-skip-permissions` ON for one run, regardless of config.

## Session data format

Sessions live in `~/.claude/projects/<path-with-dashes>/<uuid>.jsonl`. Each line is a JSON object with:

- `type`: "user" | "assistant" | "progress" | "file-history-snapshot" | "custom-title" | "mode"
- `message.content`: string or array of `{type: "text", text: "..."}` / `{type: "tool_use", name: "..."}` / `{type: "tool_result", ...}` blocks
- `sessionId`, `cwd`, `timestamp` (ISO 8601)
- `isSidechain`, `agentId` for sub-agent messages

**Session names (two formats, both supported).** A user-set session name is read in `parse_session` from `custom-title` lines (`{type: "custom-title", customTitle: "...", sessionId: "..."}`) embedded in the jsonl — last one wins, since names can be renamed mid-session. This is the current Claude Code format and takes precedence. The legacy format (`load_session_names`) reads a `name` field from `~/.claude/sessions/<pid>.json`; those files are keyed by live PID and ephemeral, so they only cover running/recent sessions and are used only as a fallback when a jsonl has no `custom-title`.

## Conventions

- Keep it a single file (`main.py`). Don't split unless it exceeds ~1500 lines.
- Colors are defined via curses color pairs in `init_colors()`. Pair constants: `C_IDX`, `C_PATH`, `C_LABEL`, `C_TEXT`, `C_SELECTED`, `C_ASSISTANT`, `C_AGENT`, `C_HEADER`.
- Use `safe_addstr()` for all curses writes — it handles screen boundary clipping.
- Tab bar lives at row 0; rendered by `draw_tab_bar(stdscr, active_tab, help_text)` and called from each tab's draw function.
- The main loop redraws on a `stdscr.timeout` (150 ms while stats load, 1 s for live status, blocking in the detail view). `getch` returns -1 on timeout; key handlers must ignore it.
- New settings: add a row to `SETTINGS_ITEMS` (key, label, help text) and a field to `Config`. Save/load round-trips JSON. The UI iterates `SETTINGS_ITEMS` automatically.
- Stats (user_msgs, assistant_msgs, agent_msgs, tool_uses, duration_min) are filled by the background loader; draw code must handle `stats_loaded == False`.

## Versioning & releases

- **Single source of truth: git tags.** `hatch-vcs` derives the package version from `git describe`. No version string is hardcoded anywhere.
- `pyproject.toml` declares `dynamic = ["version"]`; `[tool.hatch.version]` reads from VCS; `[tool.hatch.build.hooks.vcs]` writes `src/polyclaude/_version.py` at build time (gitignored).
- `main.py` reads the runtime version via `importlib.metadata.version("polyclaude")` — see `__version__` near the top.
- Between tags, builds get PEP 440 dev versions like `0.5.1.dev3+g<hash>` (or `+g<hash>.d<date>` when the tree is dirty).
- **Cutting a release**: `git tag -a vX.Y.Z -m "..."`, then `uv tool install --force --reinstall .` (locally) or push the tag (`git push --tags`) for downstream consumers. Bump rules: `feat:` → minor, `fix:`/`chore:` → patch, breaking → major.

## Install & update (end users)

Until polyclaude is on PyPI, install from source:

- **From a local clone**: `uv tool install .` (inside the repo).
- **From GitHub directly**: `uv tool install git+https://github.com/serejke/polyclaude.git`.
- **Update**: `uv tool install --reinstall git+https://github.com/serejke/polyclaude.git` — uv won't auto-upgrade git sources, so `--reinstall` is required to pull a newer commit/tag.
- **Pin to a tag**: append `@v0.5.0` (or any tag) to the git URL.

## Local development

- **Install locally**: `uv tool install --force --reinstall .` — `--reinstall` is still the safe default. With hatch-vcs every commit produces a unique version, so cache misses happen naturally; `--reinstall` only matters when iterating on uncommitted changes.
- After renaming the package, the old binary (`claude-manager`) is no longer installed by uv; only `polyclaude` exists.
